# 4단계 계획: 회원가입·로그인·결제 (2026-10-21)

원칙: 사용자 승인 없이 운영 DB 변경·회원 데이터 삭제·결제 활성화·공개 배포를 하지 않는다. 아래 "해야 할 일 중 사람 몫"은 코드로 대신할 수 없다.

## 1. 지금 있는 것
| 영역 | 상태 |
|---|---|
| 가입·로그인 | 이메일+비밀번호(이메일 확인 필요) + 구글(Lovable 인증). 화면·서버 저장·RLS 동작. 로그인 후 이동 경로 검증 추가. |
| 초대 | 코드 생성, 링크 적용(연결만). 보상은 친구의 첫 결제 때. |
| 결제 | **없음.** 모의/미구현. 결제 모드는 기본 꺼짐. |
| 엽전 | 지갑 잔액만 있었음 → 원장(`coin_ledger`) 설계 추가(검토용 SQL). |

## 2. 만들어 둔 것 (모두 검토용·미적용 / 기본 꺼짐)
- DB: 주문(`coin_orders`)·결제(`coin_purchases`)·원장(`coin_ledger`)·초대 연결(`referrals`), 서버 전용 함수 `create_coin_order`·`credit_purchase`·`refund_purchase`. 금액 고정(CHECK), 충전 멱등, 환불 시 남은 엽전 확인·초대 보상 회수.
- 앱 서버: `payments.server.ts` + 서버 함수 `createCoinOrder`·`confirmCoinOrder`. `PAYMENTS_MODE`(disabled 기본 / sandbox / live=미구현).
- 시험: PGlite(SQL) 16개, 서버 모듈 12개(실제 supabase-js 를 가짜 PostgREST 에 연결 포함).

## 3. 남은 일 (코드로 할 수 있는 것, 순서)
1. 운영 스냅샷 기준 staging 에서 SQL 재검증(동시 요청·권한 재조회) — 승인 필요.
2. ~~충전 화면(팩 1~4닢)~~ → **만들어 둠**(`/charge`, sandbox 에서만 동작, 결제 꺼짐이면 안내만). 결제 결과 화면은 PG 연동 때 보강.
3. 웹훅 수신 경로(서명 검증, 멱등) — PG 사양 확정 후.
4. ~~엽전 내역 화면~~ → **만들어 둠**(`/ledger`, 원장 SQL 이 적용돼야 내용이 나옴. 미적용이면 "준비 중" 표시).
5. 회원 탈퇴: 출생정보·지갑·초대 코드 삭제(외래키가 없어 자동 삭제 안 됨), 결제·원장 기록은 법정 보관 의무 때문에 개인 식별만 제거하는 설계 — **삭제 정책 승인 필요**.
6. 가입 방어(이메일 확인은 이미 있음): 비밀번호 길이(현재 6자 → 8자 이상 권장, 인증 설정에서 변경), 가입 시도 제한.

## 4. 사람이 해야 하는 일 (제가 확인하지 못한 항목 포함, 법적 판단 아님)
- **PG(결제대행사) 선택·계약**: 후보 예) 토스페이먼츠, 포트원 등. 사업자등록이 필요한 경우가 많다. 개인/사업자 요건과 수수료는 각 사 안내 확인.
- **사업자·세무**: 사업자등록, 통신판매업 신고, 부가세 유형(일반/간이) — 판매가 900원에 부가세가 포함되는지에 따라 실수입이 달라진다. 세무사 확인.
- **약관·정책**: 이용약관, 개인정보처리방침, 환불·청약철회 안내(디지털 콘텐츠 사용 시 제한 가능 여부 등), 미성년자 결제 처리. 법무 확인.
- **결제 기록 보관**과 탈퇴 시 처리 기준.
- 운영 비밀값: PG 비밀키(서버 전용), `RATE_LIMIT_PEPPER` 등.

## 5. 결제를 켜기 전 게이트(모두 통과해야 함)
1. staging 에서 결제 전 과정(주문→승인→충전→원장→환불→초대 보상·회수) E2E, 이중 결제·웹훅 중복·금액 변조 시도 시험.
2. 운영 SQL 적용 승인(R015 순서: 요청 제한 → 최소 권한 → 이 SQL) 및 적용 후 권한 재조회.
3. KASI 대조·엔진 검증 결과와 "정확도 고지" 문구 확정(만세력 finalApproved).
4. 약관·환불정책·사업자 정보 화면 노출.
5. 사용자(소유자)의 명시적 승인 — 그 전까지 `PAYMENTS_MODE` 는 disabled.
