**제목:** R-001~R-014 통합 정합성·만세력 정확성·전문가 검수·운영 출시 승인 게이트

**상태:** DRAFT-1 / 사용자 채택 대기 / 운영 승인 아님  
**작성 기준:** 2026-10-16  
**범위:** 기본 캐릭터, 기본사주, 심층 연애운 등 상품별로 서로 다른 승인을 수행한다.  
**최상위 원칙:** 정책 승인 ≠ 코드 작성 ≠ 자동 테스트 통과 ≠ 전문가 검증 ≠ 실제 서비스 출시 가능.

## 0. 현재 기준 감사 요약

확인 가능한 현행 아티팩트에는 R-008~R-014의 TypeScript 참조 코드·테스트가 존재한다. R-001~R-007의 동등한 독립 구현은 현재 제공된 작업 폴더에서 확인되지 않는다. '없다'는 결론이 아니라 **이번 점검 범위 내에서 확인되지 않았다**는 뜻이다. R-013 120개 월령 색인의 대다수는 2차 요약 기반이며, 전체 《궁통보감》의 조건·주용·보조·금기를 검수한 결과물이 아니다. R-014는 단일 최종 용신의 발급을 명시적으로 막고 있다.

릴리스 현황: **NO_GO**. 이 표시는 현행 유료 해석의 즉시 출시를 승인하지 않는다는 뜻이지, 구현된 참조 코드가 잘못되었다는 결론은 아니다.

## 3. 만세력 엔진 정확성

### 3.1 입력 정책
- 사용자가 입력한 출생지의 **당시 현지 법정시**와 time-zone ID(`Asia/Seoul` 등)를 수집한다. 현재 단순 `UTC+09` 고정은 금지.
- 음력인 경우 윤달 여부를 명시하고 양력으로 변환한다. 국적이나 현재 거주국으로 출생지/time-zone을 추론하지 않는다.
- 모호하거나 존재하지 않는 현지시각(DST fold/gap)은 사용자가 선택하거나 검증 가능한 출생기록을 요구하고, 임의로 한 시간을 선택하지 않는다.
- 23시 야자시 및 일주 날짜 변경, 진태양시 사용 여부는 명리학 **정책**으로 구분한다. astronomical UTC 정규화와 혼용하지 않는다.
- 진태양시 적용 여부는 임의로 선택하지 않고, 경도·균시차·표준시 차이·기준 경선을 가진 별도 정책 버전으로 남긴다.

### 3.2 절기와 간지
- **년주 경계:** 입춘을 사용할지 기타 경계를 사용할지 서비스 정책과 출처를 명시. 기본안은 입춘 절입 순간.
- **월주 경계:** 12개의 절(寅월 입춘, 卯월 경칩, 辰월 청명, 巳월 입하, 午월 망종, 未월 소서, 申월 입추, 酉월 백로, 戌월 한로, 亥월 입동, 子월 대설, 丑월 소한)을 타임스탬프로 저장. 24절기 전체의 중기와 혼동하지 않는다.
- `start <= birth_instant < next_start`를 기본 구간 정책으로 채택(경계 포함 방향 명시).
- **일주:** 알려진 기준일과의 절대일수 차를 사용하고, 달력 개혁과 경계 정책을 버전 관리.
- **시주:** 시간지·일간에서 시간간으로의 연결을 고정 표 및 전수 테스트; 시각 불명 시 복수 결과.
- 한국천문연구원 특일 API는 24절기의 **날짜 확인용**으로 활용할 수 있으나, 문서에서 시간·분·초를 제공하는지 별도 확인하기 전에는 **정밀 절입 시각 공급원**으로 인증하지 않는다. 정확한 절입 시각은 전문 천문력 또는 신뢰 가능한 천문 계산 엔진으로 확보하고 독립 비교한다.
- 천문 시간척도 TT/UT·ΔT를 사용한다면 공인 계산 라이브러리의 사용법과 불확실성을 문서화한다.

### 3.3 검증 패턴
- 입춘·경칩·청명 등 12절 각각 `T-1초, T, T+1초` 3개 경계 케이스; 전 연도군에 대해 독립 기준자료 비교.
- 1908·1912·1954·1961·1948~1960 일부·1987~1988의 한국 시간대/DST 이력; 각 연도 실재 규칙은 tzdb/별도 기록과 교차검증.
- 하루 경계 22:59:59 / 23:00:00 / 23:59:59 / 00:00:00 및 DST 애매한 시각 처리.
- 2월 29일, 윤달, 연도 음양력 변환, UTC 경계, 해외 출생, 출생시간 불명, 소수 경도.
- 권장 검증치(초안): 검증된 기준 시각과 차이 ≤60초; 절입 경계로부터 오차 허용폭 내의 입력은 계산을 유보. 이 수치는 명리학 원전 상수가 아니라 QA 시작 목표이며 실제 천문력의 정확도에 맞춰 재승인한다.
- 기준시각 없는 기대 간지나 실존 명식을 테스트에 꾸며 넣지 않는다.

## 4. 전문가 검증 절차

### 4.1 판정 데이터셋
기준 명식은 합성 테스트(수학적 불변식)와 실제 고전/전문가 명식(학파별 판단)을 별도 보관한다.

권장 초기 규모는 계산 경계 500건 이상, 일반 해석 사례 200건, 이견·특수격 경계 100건의 **출시 전 검증 목표안**이다. 이 숫자는 통계적 정확성을 입증하는 기준이 아니라 프로젝트가 선택할 QA 출발점이다.

### 4.2 전문가 판정
- 명리학 전문가 최소 2명 독립 검수, 충돌 사례는 제3의 심사자가 원전 출처·판본과 조건을 비교.
- 전문가에게 최종 정답만 받지 말고 **근거 ID, 사용 학파, 검토한 반례, 미확정 이유**를 필수로 받는다.
- 120개 《궁통보감》 조합은 개별 원문/주용/보조/조건/상순·하순/판본을 검수한다. 120개를 단일 표로 옮겼다고 검수 완료 아님.
- 합의율을 기록하되 다수결로 격국을 확정하지 않는다. 이견은 출처와 정책 차이로 관리.
- 검수자는 릴리스 승인 코드를 수정하는 사람과 분리하여 서명. 생산 운영 승인 이력 불변 보관.

### 4.3 승인 범위
`policy_accepted` → `source_checked` → `implemented` → `unit_verified` → `expert_reviewed` → `integrated` → `release_approved`. 중간 단계를 건너뛰지 않는다. 승인 범위는 '천문 계산', '십성 분류', '신강신약 후보', '최종 용신' 등 구체적인 claim type 단위.

기본 캐릭터는 `R-001+R-002+승인된 캐릭터 매핑`, 필요한 경우 R-003 등을 상품 계약(`requiredRules`)에 추가한다. 기본사주/연애운은 표시하는 claim에 따라 R-001~R-014 중 의존 규칙을 선언한다. 월간 상품 권한·5개 역년 세운의 연속 구간 같은 유료 기능 정책 역시 서버 측 시험 항목에 포함한다.

## 6. Lovable + Supabase 권장 데이터 흐름

```text
Lovable UI
  └── Supabase Auth 로그인 / 입력 검증 / 상품 설명
        └── Edge Function (JWT 검증, product contract, rate-limit)
              ├── Almanac deterministic service (절입 UTC, zone, day/hour)
              ├── R001..R014 rules + immutable approval registry (SERVER)
              ├── R015 gate + redacted evidence
              ├── credit/payment server-only atomic transaction
              └── LLM receives ONLY approved claims; generated text schema validated
                    └── analysis_runs (owner RLS) → Lovable UI
```

**브라우저가 보내면 안 되는 필드:** `approvedByRule`, `trustedRuleIds`, `ruleReleaseDigest`, `price`, `creditBalance`, `isPaid`, `finalGeju`, `finalYongshen` 등. 서버 재계산/조회.

### 6.1 DB 핵심 테이블
- `private.rule_releases`: 불변 해시, 승인자, 전문가 서명, 원전 수정 이력 (사용자 접근 금지).
- `public.analysis_runs`: 소유자, 차트의 비식별 HMAC, 사용된 규칙 manifest, 유효성·해석 JSON. 개인 출생기록 평문 저장은 피한다.
- `public.credit_wallets`: 서버만 수정하는 원장 잔액.
- `public.credit_ledger`: 서버만 추가, 소유자만 읽기, 사용자+idempotency_key UNIQUE.
- 유료 콘텐츠는 결제/크레딧 지출 전 읽기 가능한 곳에 렌더링·저장하지 않는다. 상품 이용 권한은 서버에서 판정한다.

### 6.2 RLS·권한 검증
- 모든 `public` 노출 테이블에 RLS 활성화, anon/authenticated grants를 필요한 동작으로 제한.
- User A는 A의 분석/원장만 읽기; User B 데이터는 select/insert/update/delete 우회 접근을 모두 차단.
- `service_role` 또는 신규 secret key는 브라우저에 노출하지 않는다.
- SECURITY DEFINER 함수는 schema 접근/EXECUTE grants, search_path, 내부 소유권 검사를 명시한다.
- Edge Functions에서 JWT 서명·주체·권한을 검증한 다음 관리자 클라이언트를 사용한다. 서비스 Role 키와 사용자 Bearer 헤더를 혼용하지 않는다.
- Lovable 기본 보안 스캔과 SQL 기반 RLS·grants·pgTAP·실제 두 사용자 통합 테스트를 함께 수행한다.

### 6.3 결제·크레딧·추천 보상
- 지출, 지급, 환불은 중복되지 않는 idempotency key로 처리한다.
- 동시 결제/동시 차감은 wallet row lock + 하나의 DB 트랜잭션으로 처리해 음수 잔액·이중 지출 방지.
- 결제 웹훅은 서명과 서버 측 결제금액/상품/상태 조회를 검증 후 반영한다.
- 추천인 적립은 유효 신규 사용자 검증, 자기 추천 방지, KST 날짜·월 한도, 이중 가입, 반환/취소, replay 이벤트 테스트가 필요하다.
- 클라이언트가 천문 계산이나 LLM의 cost 기록과 무관하게 결제 상태를 승인할 수 없게 한다.

## 7. LLM 안전한 출력 계약

LLM 입력에는 `claim_id`, `rule_release_digest`, `claim_status=approved`, `support_evidence_ids`, `explanation_allowed`, `uncertainties`만 전달. 후보는 '후보/검토 중'이라는 맥락에서만 설명하고 결론에 쓰지 않는다.

LLM 출력은 JSON schema, allowed claim IDs, 금지 단정 표현(예: 확정적 질병/사망/재산 예언), prompt injection, 개인정보 재노출, 테스트 패턴을 검사한다. 정형화된 분석값 변경은 항상 차단한다.

## 8. 필수 테스트 매트릭스

1. 정상/경계/오류 시각별 월주·년주·시주·일주 일관성.
2. R-003 A/B 분일이 다른 사령이라도 확정 판단으로 누락되지 않는지.
3. R-004 통근/생조 분리; R-005 일간 비견 중복 오류 방지.
4. R-006↔R-009 순환·충돌; 종격 후보 있을 때 R-012 억부 자동 차단.
5. R-007 본기 vs R-008 투간·회국 간 모순, R-010 partial rescue.
6. R-011 상신과 R-012 억부 및 R-013 조후 용어/타입 혼동 방지.
7. R-014 이론별 후보 숫자 투표와 미승인 `finalYongshen` 차단.
8. 임의 승인 ID, manifest version mismatch, cross-user chart swap 차단.
9. 결제 웹훅 중복·취소·부분환불, 잔액 부족·레이스, 추천 한도.
10. 비회원 체험과 회원가입 연동 시 다른 사용자의 유료 결과·차트 노출 방지.
11. 이메일/생년월일/결제정보가 로그·LLM 프롬프트에 불필요하게 노출되지 않는지.
12. 장애 상황에서 롤백/재시도/중복 청구/결과 기록이 일관적인지.

## 9. 출시 승인 서명

- 명리학 담당: 원전·판본·학파별 조건 서명
- 천문 계산 담당: 타임존·절입·전환 케이스 서명
- 백엔드 보안 담당: RLS·키·원장·권한 서명
- 서비스 소유자: 제품 문구·환불·고객지원·데이터 보유기간 서명

릴리스 생성: immutable manifest digest + Git revision + migration checksum + 테스트 보고서 + 서명. 기존 결과에는 사용된 릴리스 버전을 붙이고, 새 규칙으로 재계산하더라도 과거 원본 결과를 묵시적으로 덮어쓰지 않는다.
